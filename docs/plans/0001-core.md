# Plan 0001 - Core coordinator

- Design: [`docs/design/overview.md`](../design/overview.md) (v2) and review
  [`review-0001-oracle.md`](../design/review-0001-oracle.md).
- Verification (every stage): `npm run lint && npm run typecheck && npm test && npm run build`.
- Commit policy: one coherent commit per stage; push to `origin`.
- Owner questions: none open (autonomous mode; decisions recorded in the design review).
- Plan review: Momus - **PASS-WITH-CHANGES** (changes applied; see `## Review`).

## Global invariants

- one writer lane per application; enforced by `flock` + partial unique index on active tasks;
- instances isolated by XDG + `OPENCODE_DB`; overlay via `OPENCODE_CONFIG_CONTENT`;
- coordinator MCP name `hanse` is reserved; manifests cannot define it;
- runtime state lives outside managed repositories, keyed by stable project id;
- no secrets in managed repositories; credentials injected at runtime;
- forward-only migrations; timestamps UTC ISO-8601;
- Node.js `>=20`; SQLite driver is `better-sqlite3` (the `node:sqlite` fallback is rejected:
  experimental and needs Node 22.5+).

## Stage 0.5 - Vertical spike

Boundaries: throwaway script under `spike/`; no production code. Proves the riskiest assumptions.
Non-goals: anything shippable.

Deliverables: `spike/` script; `docs/journal/` directory + `docs/journal/README.md` index; a recorded
spike result under `docs/journal/`.

Acceptance criteria:

- `opencode serve` starts with isolated `XDG_*` + `OPENCODE_DB`; two instances use different DBs;
- the overlay (`OPENCODE_CONFIG_CONTENT`) is visible to the instance (coordinator MCP entry present);
- a session can be created and driven over HTTP;
- **steer** (inject a prompt into an existing session) and an **event stream** are confirmed or
  refuted, and the result is recorded;
- no state/config leakage between two instances.

QA scenarios:

- Run two `opencode serve` processes with distinct `XDG_DATA_HOME`/`OPENCODE_DB`; `curl` each
  instance's project/health endpoint; expected: distinct project/DB identities.
- `curl` create a session and send a prompt on instance A; expected: a session id and a response;
  instance B has no such session.
- Attempt a follow-up prompt to the same session (steer); expected: recorded yes/no with the exact
  endpoint used.
- Inspect the effective config for the `hanse` MCP entry; expected: present.

Risk: if steer is unavailable, Stage 5 delivery becomes poll-only (design update required).

## Stage 1 - State store, registry, CLI

Boundaries: persistence + discovery only; no opencode spawning, no queue, no MCP, no HTTP.
Non-goals: worktrees, identity, delivery.

Deliverables:

- `src/store/` - SQLite (`better-sqlite3`; add dependency) open + migrate via `schema_migrations`,
  WAL + `busy_timeout` + `synchronous=NORMAL` + `foreign_keys=ON`; full schema per design §6;
- `src/registry/` - discover/validate a project from `.hanse/project.yaml`, register project + apps.
  This **supersedes** `src/coordinator/registry.ts` (which is removed/absorbed);
- `src/runtime/` - runtime root resolution under `XDG_STATE_HOME` keyed by project id;
- CLI: `hanse init <dir>`, `hanse status [dir]`.

Acceptance criteria:

- opening a store creates/migrates the schema idempotently (running twice is a no-op);
- a discovered project and its apps are persisted with surrogate ids; `UNIQUE(project_id, app_key)`
  and FK constraints enforced;
- `status` reports the project, its apps, and instance states;
- `init` scaffolds `.hanse/project.yaml` when absent and is idempotent.

QA scenarios:

- `vitest`: migrations run twice -> schema unchanged; foreign key violation rejected.
- `hanse init <tmp>` on an empty dir; expected: `.hanse/project.yaml` created; a second run is a no-op.
- `hanse status <tmp-project-with-apps>`; expected: prints project + apps + `stopped` instances.
- `sqlite3 <db> ".tables"`; expected: the schema tables exist.

Risk: `better-sqlite3` native build (mitigation: prebuilt binaries; documented in CONTRIBUTING).

## Stage 2 - Launcher

Boundaries: instance lifecycle only; no queue/delivery; no auth.
Non-goals: multi-node, worktrees.

Deliverables:

- `src/opencode/launcher.ts` - start/stop an `opencode serve` per (project, app) with isolated env
  (extend `src/opencode/instance.ts`), compose the overlay, spawn with arg arrays (never a shell),
  record the instance row (endpoint, pid, boot_id, state), stop/health-check;
- credential strategy hook (ssh-agent / env) sufficient to clone/fetch; encryption-at-rest deferred.

Acceptance criteria: starting an instance records endpoint/pid/state; stopping clears it; a failed
spawn records `failed`; overlay is passed and isolated env applied.

QA scenarios:

- `vitest` unit: `resolveInstanceEnv` yields distinct per-app paths; overlay JSON has the reserved MCP.
- `vitest` with a fake command: spawn records `running`, stop records `stopped`; a failing command
  records `failed`.

## Stage 3 - Queue, handoff, writer lock

Boundaries: durable state machine + lock; no MCP/HTTP; no delivery to a live instance.
Non-goals: auth, approvals UI.
This stage **supersedes** the in-memory `src/coordinator/{queue,handoff,lock}.ts` stubs (the old
4-state `HandoffState` union is replaced by the 9-state machine below).

Deliverables: durable handoff queue (SQLite); handoff state machine (`queued, awaiting_approval,
dispatching, in_progress, delivered, rejected, failed, expired, cancelled`) with
attempts/next_attempt_at/expires_at/idempotency_key; `flock` writer lock per app; wait-for graph cycle
check; approval rows.

Acceptance criteria: idempotent enqueue (same key -> same handoff); illegal transitions rejected;
expiry/retry honored; lock blocks a second writer and frees on process exit; cycle A<->B detected.

QA scenarios:

- `vitest`: enqueue twice with the same idempotency key -> one handoff; invalid transition throws.
- `vitest` two-process: child holds `flock`, parent acquire fails; after the child exits, acquire
  succeeds.
- `vitest`: A->B and B->A wait graph -> cycle detected.

## Stage 4 - Identity and authn

Boundaries: principals + credentials; no delivery logic.
Deliverables: `principals` CRUD; per-instance token/identity; authn shared by API and MCP.

Acceptance criteria: an agent principal cannot approve; approvals require a human principal;
per-instance requests are attributed, not spoofable.

QA scenarios:

- `vitest`: a request as `agent` to approve a handoff -> denied; as `human` -> approved.
- `vitest`: a token bound to instance X cannot act as instance Y.

## Stage 5 - Coordinator MCP server + delivery + approvals

Deliverables: MCP server exposing `request_sibling_change` (non-blocking), `list_apps`,
`handoff_status`, `deliver_handoff`; delivery wakes the target operator session (steer if confirmed,
else poll) with the target contract + spec; approval gate; result flows back via `deliver_handoff`.

Acceptance criteria: a request returns a handoff id immediately; delivery is idempotent per handoff;
an unapproved cross-app write stays `awaiting_approval`; result recorded on the handoff.

QA scenarios:

- `vitest`: `request_sibling_change` returns a handoff id before any delivery completes.
- `vitest`: two `deliver_handoff` calls with the same id -> one result, second is a no-op.
- `vitest`: with approval required, the handoff is `awaiting_approval` until a human approves.

## Stage 6 - HTTP API + web dashboard

Deliverables: `node:http` server; server-rendered HTML: projects/apps, instance states, queue,
handoffs, approvals (approve/reject), send message. Local bind by default; documented as requiring
VPN/reverse proxy remotely.

Acceptance criteria: dashboard renders live state; approve/reject transitions a handoff; mutating
endpoints require a principal; unauthenticated mutation is rejected.

QA scenarios:

- `vitest`/`curl`: GET dashboard returns 200 with project+apps; unauthenticated POST approve -> 401;
  authenticated approve -> handoff state changes.

## Stage 7 - Secrets / git credentials

Deliverables: credential store (ssh-agent preferred; tokens encrypted at rest with a key outside the
ciphertext); git credential helper; never written into managed repos.

Acceptance criteria: a clone/fetch to a private remote succeeds using the configured credential; a
repo-wide scan finds no injected credential after clone/fetch; the key file lives outside the
ciphertext path.

QA scenarios:

- `vitest` (with a local bare remote): clone succeeds via the helper; `git -C <repo> grep -rI <token>`
  returns nothing.
- `vitest`: with no credential configured, the fetch fails with a typed error (not a crash).

## Stage 8 - Hardening and release

Deliverables: structured logging; docs; security review pass; `0.1.0` release notes.

Acceptance criteria: `npm run build` emits runnable `dist/`; a security-review artifact is written to a
named path under `docs/`; release notes exist; logs are structured (JSON lines).

QA scenarios:

- `node dist/index.js --version` -> prints `hanse 0.1.0`.
- A malformed `.hanse/project.yaml` yields a typed error and non-zero exit, not a stack trace.
